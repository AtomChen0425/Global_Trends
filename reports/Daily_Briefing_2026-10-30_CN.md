## Azure API Connections 跨租户安全风险分析

**背景**

本文揭示了 Azure Logic Apps 中 API Connections 组件存在的严重跨租户安全漏洞。这些漏洞允许攻击者利用 API Connections 的架构缺陷，绕过安全控制，完全控制其他租户连接的后端服务。研究人员通过利用这些漏洞，成功实现了跨租户的敏感信息窃取和资源访问，并因此获得了丰厚的安全奖励。

**技术实现**

核心技术问题在于 API Connections 的架构设计。Logic App 通过 Azure API Management (APIM) 实例访问后端服务。APIM 在处理连接请求时，会验证连接器的 Swagger 定义，并进行一次“密钥交换”，用用户的输入令牌替换为后端服务的配置令牌。攻击者发现，通过利用 Azure Resource Manager (ARM) 的 `DynamicInvoke` 或 `/extensions/proxy/` 接口，可以直接与 APIM 服务交互。这使得攻击者能够欺骗 APIM 实例，使其使用目标租户的连接配置令牌来访问其后端服务，从而实现跨租户的控制。文章中给出的示例展示了如何通过路径遍历（path traversal）的方式，利用 `DynamicInvoke` 端点访问其他租户的 Azure Key Vault。

**应用场景**

此漏洞的潜在应用场景极为广泛，几乎涵盖了所有通过 API Connections 集成的后端服务。攻击者一旦成功利用，便能获得对目标租户的 Azure SQL 数据库、Key Vault，以及 Jira、Salesforce 等外部服务的完全访问权限。虽然理论上可以通过配置访问令牌的最小权限来缓解风险，但实际操作中，尤其是在 OAuth 连接场景下，通常会使用初始连接者的令牌，且对于 API Key 的最小化权限配置可能被忽视，这为攻击者提供了可乘之机。

**总结**

Azure API Connections 的架构存在根本性的安全隐患，使得跨租户的完全控制成为可能。尽管存在输入验证层，但攻击者仍能通过精心构造的请求，利用路径遍历等技术绕过这些防御。此发现强调了对云服务组件进行深入的安全审计和对访问控制策略进行严格配置的重要性，以防止此类严重的安全事件发生。

现有像素空间生成式 Transformer 模型通常采用“一个像素块对应一个 token”的策略。这种方式在处理精细细节时，需要增加 token 数量，导致全局注意力计算成本急剧上升，成为模型扩展的瓶颈。研究发现，精细细节的捕捉并不总是需要更多的全局信息交互，低频结构更依赖全局信息，而高频细节则可以通过局部建模有效处理。

**技术实现**

基于上述洞察，本文提出 SpecSlot 模型，一种像素空间中的流式 Transformer。其核心创新在于解耦了输出细节与全局注意力序列长度。SpecSlot 将每个空间锚点扩展为多个“槽”（slots），每个槽负责处理离散余弦变换（DCT）系数的一个不相交频带。这种设计将锚点密度与频谱细分隔离开来。在全局注意力阶段，只有每个锚点中最低频的槽参与计算，而所有槽则进行局部交互。这种机制使得模型在不增加全局序列长度的情况下，能够提升频谱细节的建模能力。此外，一个空间头用于对频谱预测进行局部校正，而生成状态、目标和损失则保持在像素空间。

**应用场景与总结**

SpecSlot 在图像生成任务上展现出显著优势。在 ImageNet-256 数据集上，SpecSlot 在计算量相当的情况下，取得了与 JiT 控制模型相近的最终 FID 分数，并且收敛速度更快。在 ImageNet-512 数据集上，SpecSlot 在计算量减少 3.9% 的前提下，FID 分数提升了 2.84，并且以 38.2% 的更低成本，逼近了 JiT-B/16 模型的性能。在文本到图像生成任务中，SpecSlot 在 DPG-Bench 数据集上，以 40.6% 的更低前向计算成本，超越了 JiT-B/8 模型。SpecSlot 的方法为构建更高效、更精细的像素空间生成模型提供了新的思路。
